# Commit Message 生成

## 提交信息格式

严格遵循以下格式：

```
<type>(<scope>): <subject>
```

示例：`feat(auth): 新增登录页与表单校验`

## 生成流程

1. 优先运行 `git diff --staged`（可配合 `git status` 交叉确认）分析已暂存的变更，只依据暂存区内容生成提交信息
2. 仅当暂存区为空时，才回退使用 `git diff` / `git status` 分析工作区变更，并明确提示用户“当前基于未暂存的变更生成”
3. 分析变更，确定 type 与 scope
4. 用中文写一行简洁 subject（尽量不超过 20 个汉字）
5. 生成提交信息并展示给用户确认

## Type 选择

| Type     | 使用场景                     |
| -------- | ---------------------------- |
| feat     | 新功能                       |
| fix      | 缺陷修复                     |
| docs     | 仅文档变更                   |
| style    | 代码格式（不影响逻辑）       |
| refactor | 重构（既非新增功能也非修复） |
| perf     | 性能优化                     |
| test     | 测试相关                     |
| chore    | 构建、工具或依赖变更         |

## Scope 规则

- 取受影响的功能模块或目录名，用小写英文，如 `auth`、`router`、`counter`
- 单一明确模块为佳；跨多模块时选最主要的一个
- 无法确定时省略 scope，写作 `feat: xxx`

## Subject 规则

- 默认使用中文描述，简洁一行，尽量不超过 20 个汉字；仅当用户明确要求英文时才输出英文
- 描述“做了什么”，而非“改了哪些文件”
- type 与 scope 保持英文小写，整体格式严格维持 `<type>(<scope>): <subject>` 不变

## 示例

**输入**：新增用户登录页面与表单校验

```
feat(auth): 新增登录页与表单校验
```

**输入**：修复计数器在负数时显示错误的问题

```
fix(counter): 修复负数显示错误
```

**输入**：调整 README 中的安装说明

```
docs(readme): 更新安装说明
```

## 注意事项

- 一次提交只描述一件事；若变更混合多种类型，建议用户拆分提交
- 不伪造未发生的变更；仅基于实际 diff 内容生成
- 禁止将未暂存或未跟踪文件的内容混入基于暂存区生成的提交信息
- 生成后等待用户确认，不自动执行 `git commit`
