# Tazhive 前端架构说明

## 架构目标

项目采用业务功能优先的分层方式，让同一业务能力的组件、状态、类型与请求保持聚合，同时通过单向依赖降低模块耦合。目录应随真实需求增长，预留目录只用于说明扩展位置。

## 分层职责

```text
src/
├── app/                 应用启动、全局 Provider、路由、Store、全局样式
├── pages/               页面入口和页面级编排
├── widgets/             由多个下层模块组合出的页面区块
├── features/            用户可感知的独立业务能力
├── entities/            领域实体、实体模型及实体级展示
└── shared/              与具体业务无关的通用基础能力
```

### app

应用唯一的全局装配层。全局 Provider、路由实例、Store 初始化、错误边界与设计令牌放在这里。`App` 只组合应用级能力，不直接实现业务细节。

### pages

页面负责组合 widget 和 feature，并处理页面级布局。页面内部专用组件可以就近放在 `components`，但可跨页面复用的能力必须下沉到合适层级。

### widgets

Widget 是可复用的复合区块，例如导航栏、资源区或仪表盘面板。它可以组合 feature、entity 和 shared，不应初始化全局状态。

### features

Feature 表达一个完整用户能力，例如登录、搜索或计数。推荐内部结构如下：

```text
features/example/
├── api/          # 业务请求与传输模型
├── components/   # feature 展示和交互组件
├── hooks/        # feature 状态、副作用与编排逻辑
├── lib/          # feature 私有纯函数
├── types/        # feature 私有类型
└── index.ts      # 唯一公共出口
```

只创建当前需要的子目录，不为形式完整制造空文件。

### entities

Entity 表示稳定领域概念，例如用户、组织或订单。它可以包含领域模型、实体级组件和实体请求，但不依赖具体用户操作流程。

### shared

Shared 只能包含无业务含义的代码，例如通用按钮、HTTP 客户端、日期函数、基础类型和环境配置。禁止把暂时不知道放哪里的代码统一丢入 `shared`。

## 依赖规则

允许的依赖方向为：

```text
app → pages → widgets/features → entities → shared
```

- 上层可以依赖同层模块或下层模块，下层不得导入上层。
- 同层业务模块不得读取对方内部文件；需要协作时使用公共出口或提升组合层级。
- 模块内部使用相对路径，跨模块使用 `@/` 路径别名。
- 外部消费者只能从模块根部 `index.ts` 导入，禁止 `@/features/example/hooks/useExample` 一类深层导入。
- 公共出口只暴露消费者真正需要的组件和类型，内部 Hook、实现类型与工具函数保持私有。

## 数据与状态流

- 服务端数据请求放在 feature 或 entity 的 `api`；无业务含义的请求客户端放在 `shared/api`。
- 请求响应先转换为领域或界面模型，再进入组件，禁止传输层字段散布到页面。
- 组件局部状态优先使用 React 状态；可复用交互状态进入 feature Hook。
- 只有跨页面、跨业务且生命周期确实全局的状态才进入 `app/store`。
- 页面通过 Props 和公共 Hook 组合数据，避免隐藏的跨模块可变状态。

## 新增业务模块流程

1. 判断能力属于页面编排、复合区块、业务动作、领域实体还是无业务基础设施。
2. 在对应层创建以业务名命名的目录，并只创建实际需要的子目录。
3. 将状态与副作用放入 Hook，将展示拆成组件，将类型和静态数据就近保存。
4. 在模块根部建立最小 `index.ts` 公共出口。
5. 使用 `@/` 从消费模块导入，并检查依赖方向没有反转。
6. 执行 `pnpm check` 和 `pnpm build`，再进行页面冒烟验证。
